# /sql生成

目标：由 Claude 直接把用户需求转换为语义明确、字段可追溯、符合目标方言且便于验证的 SQL。生成的重点不是“拼出能看的语句”，而是先建立结果契约和数据来源，再安全表达业务逻辑。

不要依赖意图路由、槽位填充引擎、SQL 模板库或旧流程状态。用户输入和 MCP 事实就是当前上下文；只有阻断正确性的缺口才使用 `AskUserQuestion`。

## 输入判断

直接理解以下信息：

- **结果契约**：要回答的业务问题、明细/汇总类型、输出粒度、字段及顺序、排序和数量要求。
- **指标口径**：指标定义、聚合方式、去重对象、NULL 处理、金额精度、状态范围和有效记录条件。
- **维度与范围**：分组维度、业务过滤、时间范围、时区、业务时间字段和分区时间字段。
- **数据来源**：明确表、候选表、库、字段、业务术语、参考 SQL 和允许使用的数据域。
- **关联契约**：主表、辅表、join type、join key、基数、唯一性和未匹配行保留规则。
- **运行环境**：SQL 方言、引擎与版本、默认库、模板变量和允许的函数/UDF。
- **交付约束**：只读查询或写入 SQL、目标表/分区、是否允许 CTE、注释和最小兼容版本。

用户提供参考 SQL 时只把它作为口径或写法证据；除非用户明确要求，不擅自改写参考 SQL，也不把其中未验证的表字段推广成平台事实。

## 触发澄清

遇到以下阻断情况时调用 `AskUserQuestion`：

- 无法确定结果目标、输出粒度或核心指标。
- 同一指标存在多个合理口径，例如支付金额、订单金额、退款后净额。
- 缺少时间范围，且用户要的是特定周期结果或生产查询。
- 候选主表、字段、join key 或时间字段不唯一，选择不同候选会改变结果。
- 去重、NULL、未匹配行、时区或状态范围会影响结果，但用户和元数据都没有给出依据。
- 用户要求写入 SQL，但目标表、列映射、覆盖方式或分区范围不明确。
- 用户要求生产可用 SQL，但关键表/字段没有用户输入或已实现 MCP 事实来源。

用户明确要求“先给骨架”时可以带占位符继续，但必须显式标记为不可直接执行。MCP 不可用而用户已给出完整、可信的表字段时可以继续，并说明未做元数据验证。

## MCP 取数流程

读取 `references/mcp-interfaces.md`，只调用其中明确标记为“已实现”的工具，并按最小范围取数：

1. 有明确 `db.table` 时，先调用 `hive_get_table(includeColumns=true, includePartitions=true)`；只在需要存储属性或完整定义时补 `hive_get_table_ddl`。
2. 只有表名或业务关键词时，调用 `hive_search_tables`；候选过多时澄清，不循环更换同义词扩大搜索。
3. 只获取实际会用于输出、过滤、关联、分组和写入的字段；用 `hive_get_columns` 确认名称、类型、注释和分区标记。
4. 时间查询用 `hive_get_partitions` 确认分区结构和可见分区，但不把“存在某个分区”推断成业务应查询该分区。
5. 字段来源不清时用 `hive_find_column_usage` 找候选表；返回多个候选时不能自行挑选。
6. join 或去重需要唯一性依据时用 `data_map_get_table_primary_keys`；主键记录为空时不臆造关联键，存在主键也不等同于业务数据绝对无重复。
7. 函数或 UDF 是否可用、签名是否匹配不确定时，用 `hive_function_search/get` 核对目标 HiveServer2 的实际注册信息。
8. 涉及近期落盘时可调用 `hive_table_freshness_get`；业务术语、业务 SLA 或历史实际算子计划尚不可验证时，只记录对应缺口。

不要预加载业务域所有表，也不要为生成一条 SQL 获取无关运行历史和 YARN 数据。

## 生成流程

1. **确定结果契约**：用一句话锁定业务问题、粒度、指标、维度、时间和输出要求。
2. **选择数据源**：优先使用直接承载目标粒度和指标、字段来源完整且时间范围匹配的表；表名相似不是选择依据。
3. **建立字段映射**：为每个输出、过滤、join、group、order 和写入字段标记来源；计算字段写清表达式和口径。
4. **设计基数变化**：逐步判断过滤、join、聚合、distinct、窗口和集合操作如何改变行数与粒度，防止 join 放大或错误去重。
5. **设计时间条件**：区分业务时间与分区时间，保持时区和边界一致；分区过滤服务于扫描范围，业务时间过滤服务于结果口径，两者不能互相冒充。
6. **设计关联**：只使用已确认 key 和 join type；明确一对一、一对多、多对多及未匹配行保留规则。
7. **设计计算**：确认聚合、NULL、Decimal 精度、除零、日期函数、窗口 frame、排序稳定性和集合去重语义。
8. **设计写入**：仅在用户明确要求时生成写入 SQL；保持目标列顺序和分区语义，不生成 DDL，不扩大 overwrite 范围。
9. **生成 SQL**：结构简单时直接表达；复杂时用职责清晰的 CTE 分隔过滤、去重、聚合和关联，但不为形式统一制造多余层级。
10. **验证草案**：静态复查字段作用域、别名、group by、join、时间边界和结果契约；解析器或计划工具已实现时再按需验证，否则明确限制。

## SQL 编写规则

- 不默认使用 `select *`，不臆造字段名；字段不完整时只能给明确的不可执行骨架。
- 不添加用户未要求的业务过滤、`limit`、排序、去重、默认状态或“近 N 天”条件。
- 不因为字段同名就推断 join key，不因为主键存在就自行决定维表保留哪一行。
- join key 类型不一致时不静默强转；先确认目标类型、异常值、精度和 NULL 规则。
- outer join 的过滤条件保留在符合未匹配行语义的位置，不能随意在 `ON` 与 `WHERE` 间移动。
- `count(*)`、`count(col)`、`count(distinct col)` 和多列 distinct 必须对应明确口径。
- 窗口函数必须明确 partition、order、frame；需要稳定首行/末行时排序键应能稳定决胜。
- 时间边界优先使用半开区间表达连续时间范围，并保持用户指定的时区和字段类型。
- 分区字段过滤避免无依据的函数包裹和隐式类型转换，但不能为了裁剪改变业务时间范围。
- `union` 与 `union all` 依据重复行契约选择，不以性能理由默认互换。
- 方言或函数版本不确定时，使用保守语法或澄清，不创造不存在的 UDF。
- 写入 SQL 必须显式保护目标、列映射和分区范围；不生成自动 DDL，也不执行 DDL/DML。

## 输出格式

根据问题自然组织中文 Markdown，不强制输出空章节。结果应覆盖：

- **结果定义**：业务目标、粒度、时间和关键口径。
- **SQL**：可靠时使用 `sql` fenced code block 给完整 SQL；信息不足时给明确标记的不可执行骨架。
- **字段与数据来源**：只列关键表、字段、分区和关联依据，并标明来自用户还是 MCP。
- **假设与限制**：区分已确认事实、用户假设和未实现能力导致的验证缺口。
- **验证重点**：说明应校验的行数、重复、NULL、边界时间、聚合值或写入范围；不声称已经执行。

## 质量闸门

输出前确认：

- 每个表、字段、分区、函数和 join key 都有用户输入或 MCP 事实来源。
- 结果粒度、指标口径和每一步基数变化可以解释，没有隐式去重或 join 放大。
- 业务时间、分区时间、时区和开闭区间没有混淆。
- 没有擅自添加 `limit`、排序、状态、时间、去重或业务默认值。
- 写入 SQL 没有改变目标列映射、覆盖范围或分区语义，也没有生成 DDL。
- 方言、类型、NULL、Decimal、窗口和集合操作风险已经检查。
- 未实现的业务术语、业务 SLA 和历史实际计划能力没有被包装成已验证事实。
- 没有声称 SQL 已解析、已执行、结果正确或性能已验证。
