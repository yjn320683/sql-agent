# /sql解释

目标：由 Claude 根据用户关注点解释 SQL 的结果契约、逻辑变换、字段来源、表关系以及可获得的计划或运行事实。默认只解释，不擅自改写、修复或优化 SQL。

必须区分三种完全不同的内容：SQL 文本能证明的逻辑语义、Explain 提供的预测/物理计划、目标运行产生的实际执行事实。不要把 SQL 书写顺序称为引擎真实执行顺序。

## 输入判断

直接理解以下信息：

- 完整 SQL 或用户指定片段，以及模板变量、默认库和 SQL 方言。
- 用户关注点：业务作用、输出字段、粒度、CTE、join、过滤、聚合、窗口、写入、计划或实际慢点。
- 表/字段元数据、业务术语、参考 SQL、DDL 和主键记录。
- 如果解释真实执行：Query ID、Application ID、MR Job ID、运行时间和相关指标。
- 期望深度：面向业务、开发调试、代码评审或执行诊断。

用户只问局部时聚焦该片段，但要读取保证局部语义所需的最小上下文，例如别名定义、outer join 类型、窗口定义或上游 CTE。

## 触发澄清

遇到以下阻断情况时调用 `AskUserQuestion`：

- `sql_task_get` 无法取得任务 SQL；用户只问局部逻辑时，则是没有说明明确片段。
- 片段缺少定义，导致字段作用域、别名、CTE 输入或输出无法判断。
- 用户问结果是否“正确”，但业务口径、粒度或期望结果不明确。
- 用户问某次真实运行为什么慢/失败，却没有可定位运行的标识或计划/指标，且已实现工具无法检索。
- 同一字段、指标或时间条件存在多个业务解释，选择会改变结论。

没有元数据时仍可解释 SQL 文本结构，但表字段业务含义必须标记为未知或命名推断。不要为补充非关键背景连续追问。

## MCP 取数流程

读取 `references/mcp-interfaces.md`，只调用已实现工具，并围绕用户关注点取数：

0. 获取原任务预测计划时调用 `hive_task_sql_explain(taskId)`，禁止复制或重构任务 SQL 后调用 `hive_sql_explain`。
1. 表/字段含义、类型、注释或分区角色不明确时，用 `hive_get_table`、`hive_get_columns` 和必要的 `hive_get_partitions`。
2. 解释表属性、存储格式、写入列或完整定义时用 `hive_get_table_ddl`。
3. 字段来源在当前 SQL 外部且不明确时，用 `hive_find_column_usage` 获取候选，不把候选写成确定血缘。
4. 解释 join 唯一性或结果粒度时用 `data_map_get_table_primary_keys`；主键记录只是元数据事实，不能证明本次运行无重复。
5. 涉及近期落盘时可调用 `hive_table_freshness_get`；业务术语、字段血缘、表关系、业务 SLA 和历史实际算子计划未实现时，明确对应解释层缺失。
6. 解释真实运行时必须先确认 Query/Application/Job 映射和完整 Job 集合，再解释 Job、Task、Counter 与异常 Attempt。

不要为了单个字段解释预加载所有表，也不要在用户没问执行问题时获取 JobHistory/YARN 数据。

## 解释流程

1. **确定解释层级**：业务结果、逻辑 SQL、字段血缘、预测计划或实际运行，只展开用户需要的层级。
2. **说明结果契约**：先解释最终输出的粒度、字段、过滤范围、重复行、排序和写入目标。
3. **建立查询块**：识别 CTE、子查询、集合分支和最终查询，为每个块说明输入、变换、输出粒度和被谁引用。
4. **解释字段来源**：追踪直接列、表达式、聚合、窗口和条件分支；无法追到真实表字段时停止，不猜测。
5. **解释基数变化**：说明过滤、join、group by、distinct、窗口筛选、union 和 limit 如何改变或保留行数与粒度。
6. **解释关键语义**：特别说明 outer/semi/anti join、NULL 三值逻辑、时间边界、去重、窗口 frame、全局排序和写入覆盖范围。
7. **关联元数据**：补充已确认的字段类型、分区、主键记录、DDL 和注释；与 SQL 冲突时显式指出。
8. **解释计划**：只有拿到计划时才说明 stage、算子、分区裁剪、join 策略和并行度，并标记 `actual` 或 `predicted` 来源。
9. **解释实际运行**：只有拿到目标运行事实时才从 Query 映射到完整 MR Job 集合和 Task，说明耗时、shuffle、spill、资源或失败；不要只复述 Application 汇总。
10. **指出风险与未知**：区分确定语义、元数据事实、执行事实和推断。风险提示不自动变成优化方案。

复杂 SQL 可以使用简洁 Mermaid 流程图展示 CTE/表到输出的关系；节点名称使用真实查询块或表名，不虚构业务实体。简单 SQL 不画图。

## 解释约束

- 逻辑解释描述“SQL 要求什么”，实际执行解释描述“引擎这次做了什么”，两者不能混用。
- SQL 的 FROM/JOIN/WHERE/GROUP/HAVING/WINDOW/SELECT/ORDER 逻辑关系不等于物理执行时间顺序。
- 不把字段命名、表名或注释推断写成已确认业务口径。
- 不把主键记录自动解释成 join 一对一，也不忽略 outer join 未匹配行。
- 不把 CTE 描述成必然物化；是否内联或复用取决于引擎和计划。
- 不把 `order by`、窗口排序和文件内部顺序混为一谈。
- 不输出用户未要求的改写 SQL，不用 `/sql优化` 或 `/sql修复` 的规则替代解释。

## 输出格式

根据用户关注点自然组织中文 Markdown，不强制输出空章节。可包含：

- **整体作用与结果粒度**：一句话概括最终结果。
- **逻辑链路**：按查询块和基数变化解释，不冒充物理执行顺序。
- **关键字段与表关系**：给出来源、表达式、join 和已确认元数据。
- **计划/运行说明**：仅在有真实数据时输出，并标明 actual/predicted、目标运行和时间范围。
- **风险与未知**：列出 NULL、重复、时间、关联、写入以及缺失事实。

## 质量闸门

输出前确认：

- 已先回答用户真正关注的问题，没有用全量讲解淹没局部问题。
- 结果粒度、字段来源和每一步基数变化可以追溯到 SQL 或 MCP。
- 已严格区分逻辑语义、预测计划和实际运行事实。
- 没有把 SQL 书写顺序称为真实执行顺序，也没有把 CTE 说成必然物化。
- 没有把字段命名推断、候选血缘或主键记录夸大成业务事实。
- 计划和运行说明绑定了正确 Query/Job 集合和时间范围，没有伪造耗时或执行路径。
- 没有擅自改写、修复或优化 SQL。
- 未实现能力和元数据缺口已经明确说明。
