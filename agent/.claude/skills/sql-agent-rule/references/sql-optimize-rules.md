# SQL 优化规则库

本文件只在 `/sql优化` 中读取。它用于把运行现象、计划算子、数据特征和 SQL 结构关联成候选原因，不用于替代真实执行计划、运行事实或目标引擎验证。

## 使用方法

1. 只检查与目标 SQL 实际结构相关的规则。
2. 有运行数据时先找慢路径，再映射计划算子和相关 SQL；没有运行数据时才从 SQL 风险开始。
3. 对每个候选项评估预计收益、事实来源、语义风险和验证方式。
4. 只有高收益或明确低风险的项进入主要结论，最多 5 条。
5. 改写前读取 `sql-equivalence-checklist.md`，不能证明等价时只给建议。

## 量化与等价性底线

- 没有可比的实际 Job、Task 和 Counter 基线时，不给出性能收益百分比、倍数或固定耗时预测。
- 平均文件大小只能作为布局事实；未结合集群块大小、InputFormat、任务时长和实际 Map 数时，不直接定性为“小文件问题”。
- 主键登记、DDL 注释中的“唯一”和预测计划基数都不能证明运行数据唯一。涉及把窗口去重移动到 join 前、合并 join 或改变关联顺序时，必须验证右表每个 join key 的真实唯一性，否则不得声称结果等价。
- 需要 DDL、文件合并或表格式变更的建议归类为外部治理候选，不提供可直接执行 DDL，不计入当前 SQL 可立即落地的改写。

## 证据来源

使用 `sql-optimize-data.md` 中的 `SQL`、`META`、`PLAN`、`RUN`、`ENV`、`HYP` 标签。不要把来源标签当作机械评分：

- 真实根因通常需要 `RUN` 证明现象，并由 `PLAN`、`META` 或 `ENV` 解释原因。
- `SQL` 能确认结构和语义风险，但通常不能独立证明某算子是实际耗时瓶颈。
- 缺少运行事实时仍可输出静态风险，但必须标记为 `HYP`，不得编造耗时、扫描量、shuffle 大小或提升百分比。

## 规则矩阵

| 类别 | 可观察信号 | 需要补充的事实 | 允许的低风险动作 | 主要语义风险 |
| --- | --- | --- | --- | --- |
| 投影裁剪 | `select *`、读取未使用大字段 | 完整输出字段、字段清单 | 明确列出必需字段 | 漏列、字段顺序变化 |
| 分区裁剪 | 无分区过滤、分区字段被函数包裹 | 分区字段、类型、目标时间范围 | 使用与分区类型一致的直接谓词 | 时间边界、时区、动态分区语义变化 |
| 过滤下推 | 高选择性过滤在 join/聚合之后 | 外连接语义、过滤字段来源 | 下推到语义等价的输入侧 | outer join 被隐式改成 inner join |
| 重复扫描 | 同一大表被多个等价子查询读取 | CTE 是否物化、引擎版本 | 合并可共享且语义一致的扫描 | CTE 内联后不一定减少扫描 |
| join key | key 上存在函数、cast、表达式 | 两侧字段类型、空值规则 | 在上游统一类型或使用原生同类型 key | cast 截断、格式异常、NULL 匹配变化 |
| join 放大 | 非唯一维表、多对多 key、join 后再 distinct | 主键、唯一性、基数、过滤条件 | 先按明确业务键去重或聚合 | 错误吞掉合法重复行 |
| join hint | 用户要求 broadcast/mapjoin/skew hint | 表大小、引擎版本、执行计划 | 证据充分时作为可选方案 | OOM、版本不兼容、计划退化 |
| 聚合 | 大范围 group by、重复聚合、无效分组列 | 输入粒度、输出粒度 | 提前过滤、同粒度预聚合 | 聚合层级和重复计数变化 |
| distinct | 多列 distinct、join 后 distinct | 重复来源、结果去重要求 | 先消除已确认的重复来源 | 删除合法重复、NULL 组合变化 |
| 窗口函数 | 多个相同窗口、宽输入排序、全量 row_number | partition/order/frame、TopN 语义 | 提前过滤和裁列、复用相同窗口定义 | 并列顺序不稳定、frame 变化 |
| 全局排序 | 无必要的 `order by`、超大结果排序 | 是否要求全局有序、limit 语义 | 用户不要求全局顺序时给可选局部方案 | 输出顺序契约变化 |
| 集合操作 | `union` 用于无需去重的集合 | 是否允许重复、分支是否互斥 | 仅在明确允许重复时改 `union all` | 结果重复行变化 |
| 子查询 | 相关子查询可能逐行计算 | 引擎优化能力、NULL 语义 | 可证明等价时改 join/semi join | 多行子查询、NULL 和重复语义变化 |
| 表达式 | 重复复杂表达式、无必要 cast/coalesce | 类型、NULL 默认值、溢出规则 | 提前计算并复用完全相同表达式 | 精度、短路和 NULL 结果变化 |
| 写入 SQL | `insert overwrite`、动态分区写入 | 目标表 DDL、分区策略 | 仅优化读取侧，不改变写入目标和模式 | 覆盖范围、列映射、动态分区变化 |

## Hive on MapReduce 诊断规则

先确认目标 Query/Application/Job 映射和完整 Job 集合，再使用以下信号。任何单一指标都不应直接触发改写。

| 运行现象 | 需要关联的事实 | 候选原因 | 优化方向 |
| --- | --- | --- | --- |
| 总耗时长但 MR Job 执行占比低 | Job submit/start、YARN Application 时间、用户提供的 HS2 时间线 | 排队、启动、元数据或客户端瓶颈 | 优先处理调度/平台问题，不先改 SQL |
| 单个 MR Job 占总执行时间大部分 | Job Counter、Map/Reduce task 分布、预测 Explain | 大扫描、join、聚合、排序或写入热点 | 聚焦该 Job 对应的候选 stage 和相关 SQL |
| task duration 或 input 的 max 远高于 p50 | join/group key 分布、partition/file 分布、慢节点 | 数据倾斜、分区倾斜、小文件或节点异常 | 区分数据、存储和节点原因后再选方案 |
| shuffle 大且下游明显放大 | join 基数、NDV/TopN、join strategy、输入输出 records | 多对多 join、过滤过晚、错误估算 | 过滤/预聚合、修正统计或有依据的 join 策略 |
| spill 高、GC 高、OOM 或 physical memory exceeded | 容器规格、峰值内存、sort/shuffle buffer、并发 task | 单 task 数据过大、容器不足或参数不匹配 | 先缩减数据与单 task 压力，再评估参数 |
| failed fetch、重试和长尾同时上升 | shuffle 服务、节点、attempt 日志、网络/磁盘 | 节点或基础设施异常，也可能由超大 shuffle 放大 | 区分平台故障与 SQL 触发因素 |
| task 数很多且单 task 很短 | 文件数/大小、input split、Job 启动 | 小文件、过度并行或启动开销 | 合理合并文件/输入，不盲目减少并行度 |
| task 数少且每个 task 输入巨大 | reducer parallelism、grouping、可用容器、数据量 | 并行度不足或单分区过大 | 基于数据量和资源评估并行度 |
| 估算行数与实际行数偏差大 | 统计时间/完整性、NDV/NULL、plan join strategy | 统计过期/缺失导致 CBO 选错计划 | 优先修正统计，再比较计划 |
| Application 多次 attempt、抢占或长期 pending | queue capacity、用户限额、preemption、集群快照 | 队列或资源竞争 | 调度层处理，SQL 改写只作为降低资源的辅助 |

### 运行日志处理

- 先使用结构化状态、counters 和退出码；日志用于补充异常原因。
- 只取异常签名、次数、首次/末次时间和少量脱敏片段，不加载全部 container 日志。
- OOM、fetch failure、preemption、node lost 等错误必须关联到具体 Job、Task Attempt 和时间，不能因诊断中出现一次关键字就定性整条查询。

## Hive 重点规则

### 分区与谓词

- 用 `hive_get_table(includePartitions=true)` 或 `hive_get_partitions` 确认分区字段后，再判断是否命中分区裁剪。
- 分区字段上的 `date()`, `substr()`, `cast()` 或算术表达式只是风险信号；是否失去裁剪取决于引擎版本和表达式，不能直接声称全表扫描。
- 不擅自补“近 30 天”等业务条件。用户未给时间范围且优化依赖该条件时，调用 `AskUserQuestion`。
- 谓词常量类型应与分区字段类型一致，避免隐式转换；修改前确认字段类型。

### Join

- 外连接中，右表过滤从 `ON` 移到 `WHERE` 常会改变结果；默认禁止。
- 维表去重必须有稳定业务键和保留规则。只有主键并不足以决定保留哪一行。
- 没有表大小或 Explain Plan 时，不主动添加 `MAPJOIN`、broadcast 或 skew hint。
- join 顺序对不同 Hive/MapReduce 版本的优化器影响不同；没有执行事实时，只说明候选，不声称一定更快。

### 聚合、窗口与排序

- `count(distinct x)` 改近似算法不是等价优化，只能作为用户确认后的近似方案。
- `row_number() = 1` 去重必须保留原 `partition by` 和完整排序规则；排序键不唯一时提示结果可能不稳定。
- `order by` 保证全局顺序，不能直接改成 `sort by`、`distribute by` 或 `cluster by` 并宣称等价。
- 不为全局 `order by` 自动添加 `limit`；TopN 和完整有序结果是不同的结果契约。
- CTE 在部分引擎版本中会被内联；抽成 CTE 主要提升可读性，不自动等于减少计算。

### NOT IN 与无收益改写

- `not in (subquery)` 在子查询结果含 NULL 时可能使谓词整体变为 UNKNOWN；改成普通 `not exists` 会改变结果，除非显式保留相同 NULL 语义。
- `not in ('A', 'B')` 改成对常量 CTE 的 `not exists` 通常只增加结构复杂度，没有可证明性能收益；不要把它列为优化。
- 用户指定的写法调整若没有性能证据，可以解释并给出可选写法，但必须标记为“非性能优化”。

## 排序与取舍

候选优化点按以下顺序排序：

1. 已由 `RUN` 锁定热路径、由 `PLAN/META/ENV` 解释原因，且语义风险低的动作。
2. 已确认属于队列、节点、Metastore、锁或其它平台问题时，先给对应处理方向，不强行产出 SQL 改写。
3. 能减少热路径输入、join 放大、shuffle、spill 或 task 长尾，且结果契约可证明不变的动作。
4. 没有运行事实时，按已确认的分区裁剪、过滤下推、投影裁剪、join、聚合和排序风险排序，并统一标记为待运行验证。
5. 只有运行或计划事实才能确认的建议，不能从 SQL 信号直接写成确定根因。
6. 纯格式、别名和无收益改写不计入优化点。
